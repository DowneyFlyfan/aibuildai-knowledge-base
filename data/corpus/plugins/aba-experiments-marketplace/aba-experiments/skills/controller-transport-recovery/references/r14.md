# R14: transport expiry, real refusal, and same-run recovery

Observed on 2026-11-08. The active agent's model relay was unavailable while its controller process and four owned supervision processes remained alive. The remote, same-network-namespace Transmission Control Protocol check returned `ConnectionRefusedError`, error number 111. A read-only model-list request failed too. The controller retried requests, but the journal contained clock heartbeats without first model responses or tool activity. Owned training processes and graphics-processor usage were zero at that failure observation.

The prior relay/tunnel lifetime had expired. A fresh administrative run authorization had not renewed the transport. This motivated checking actual transport lifetime as well as reachability before subsequent launches and first-clock creation; these checks must not reset a clock that already started.

After explicit user authorization to restart the failed relay, the operator authenticated that the old gateway/tunnel handles were absent, restarted the existing configuration using its existing local credentials, and published lifetime metadata derived from the actual launches and timeouts. Local and remote health checks returned 200. The verified conservative transport expiry covered the existing run's administrative deadline.

The existing native controller subsequently produced an actual response event, then completed a `Bash` tool call without error; usage identified `gpt-6-sol`. This established real controller recovery in the same active Run. Later numerical model restoration and update 28 were separately observed and are documented in the two-turn-learning skill.

The exact training-window file digest was unchanged across repair. No native Run restart, new clock, credential copying, or replacement model configuration was needed. This observed sequence supports the transport diagnosis; it is not a controlled experiment establishing the controller model's causal effect on training quality.
